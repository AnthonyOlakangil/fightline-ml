Project

ufc-predictor — a UFC fight-outcome model that is tested against the betting market and used to price parlays by simulation. This is a portfolio project whose primary reader is a technical recruiter or hiring engineer. Correctness and reproducibility matter more than feature count. A smaller project that is provably leak-free and beats a fair baseline is worth far more than a large one with hidden data leakage.

Every claim in the README must be reproducible from the repo by someone who clones it and runs one command.
Results must be honest. If the model does not beat the market, say so and show it. A rigorous negative result is a strong portfolio piece; a fabricated positive one is disqualifying.
No hardcoded metrics, no placeholder numbers, no "example" results committed as if real. Numbers in the README are generated by scripts and regenerable.

Non-negotiable engineering rules
Point-in-time correctness. Every feature for a fight must be computable using only data available strictly before that fight. No future information, ever. Build features with as-of joins. This is the #1 way this project silently fails and the #1 thing a reviewer will check.
Leakage tests are mandatory. There is a tests/test_leakage.py suite that asserts no feature row uses any event dated on or after the fight it describes. The backtest is walk-forward: train only on fights before event date t, predict event t, advance. A test asserts the training cutoff is respected.
Determinism. All randomness takes a seed. Same seed → same numbers. Seeds live in config, not scattered literals.
Fail loudly. If a scrape returns an unexpected shape, a join drops rows, or a date can't parse, raise — do not silently continue with partial data. Log row counts at each pipeline stage.
No real-money framing. This is a research backtest. The README states plainly it is not betting advice and nothing here should be used to wager. Keep the tone analytical.
Cache raw data in the repo. Commit a dated snapshot of the cleaned raw data (Parquet) so the repo runs end-to-end without re-scraping. Scrapers exist and are documented, but the graded path must not depend on a live site being up.
Stack (fixed unless you flag a blocker)
Python 3.11, dependencies managed with uv, pinned in pyproject.toml + uv.lock.
Scrape: requests + beautifulsoup4, polite rate limiting, on-disk response cache.
Store: Parquet files queried with DuckDB. Tables: fighters, fights, fight_stats (per round), odds.
Models: scikit-learn, LightGBM. Bayesian model (NumPyro) is a stretch module, isolated so it can be skipped.
Sim/metrics: NumPy, scikit-learn metrics, matplotlib.
CLI: Typer.
Demo UI: Streamlit.
Tests: pytest (includes the leakage suite). Lint/format: ruff. Both run in CI.
Everything orchestrated by a Makefile / uv run tasks.
Data sources (in priority order)
UFCStats (ufcstats.com) — fights, per-round stats, fighter attributes. Reliable to scrape; this is the canonical source.
Historical closing odds — the real bottleneck. Prefer a reproducible public dataset (search Kaggle for UFC odds datasets that include closing lines) committed as a snapshot. Document exactly which dataset, its license, and its date coverage. A BestFightOdds scraper is an acceptable documented fallback, rate-limited and cached. Kalshi/live books only for the two upcoming live cards, if reachable.
If a source can't be reached from this environment, say so, commit the cached snapshot path you're using, and keep going — do not stall.

Convert American/decimal odds to implied probabilities and remove the vig (two-sided normalization) before any comparison. The market baseline is the vig-free favorite.
